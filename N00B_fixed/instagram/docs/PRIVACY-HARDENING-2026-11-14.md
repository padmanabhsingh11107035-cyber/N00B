## N11: reading other people's profile data straight from the table
**What was wrong.** Any signed-in person could ask the database directly (not through the app) for `city`, `privacy_settings`, `extra`, `noob_points` and `is_suspended` of every account, including accounts that hid from them or are suspended, and for the whole follow table (private accounts' followers and following).

**What changed.**
* The five columns above are closed to the API (same method as the four Pro/shop columns before). The database's own functions still read them, so every answer of the app is identical (the test compares 72 answers of `search_users`, `user_by_id`, `get_my_user` for eight kinds of reader before and after: identical).
* Columns still readable straight from the table (everything else): id, legacy_id, username, display_name, avatar, bio, account_type, is_business, business_category, is_verified, verification_tier, is_admin, is_ai, is_live_avatar, live_avatar_video_url, website, pronouns, interests, social_links, external_links, custom_links, cross_profiles, status_note, games_won_count, games_played_count, pro_tier, followers_count, following_count, posts_count, created_at. The app itself reads only `id, username, display_name, avatar, is_verified` of the person's OWN row.
* The one direct read of a closed column (the "am I suspended?" check in `checkSessionStatus`) now calls the new function `my_suspension_status()` (`src/services/supabaseApi.ts`, with a fallback to the old read for a database that does not have it yet). Note: `my_account_status` already existed (Settings hub), so the new one has another name.
* `follows_select` (who can read follow rows): a row involving a PRIVATE account is visible only to that account, to people who follow it, and to the other person in the row. Public accounts, hidden-from-me and deleted accounts: as before. New helper `can_see_follow_edges_of(uuid)`.
* `scripts/security-audit-db.mjs`: the five columns are added to its closed list (it passes).

**Risk / what you may notice.**
* "Followed by ..." on the profile of a private account you do NOT follow is now empty (it used to list who follows that account). On accounts you follow, nothing changes.
* The audit found **no other place** (src, edge functions, scripts) that reads these columns as a signed-in person. Edge functions use the service key and are unaffected.
* **Not closed (honest limit):** (1) a hidden or suspended account's basic fields (username, display name, bio, avatar, counters) are still readable straight from the table by a signed-in person, because many list functions join the table with the reader's own rights and a row rule on `profiles` would blank names in chats, comments and notifications. (2) `user_public_json` includes `followingIds` (who an account follows) for every account, private ones too: the app builds Followers/Following lists from it. The follow table is now protected, this function output is not. Closing it needs a change of how the lists are built (a follow-up, not done to avoid breaking lists). (3) Live check scripts `scripts/live-check-phase1.mjs` (noob_points) and `live-check-phase4.mjs` (is_suspended) read those columns directly and will report a failure; they are manual scripts, not part of the guard.

## N12: `match_contacts` (phone number lookup)
Now: 500 numbers per call, 10 calls an hour and 30 a day per person (counter table `api_rate_limits`, internal), friendly error text ("You have searched your contacts a lot just now. Please try again in an hour."), and hidden and suspended accounts are no longer returned. Same output shape and grants. The app sends the contact list in pieces of 500 (at most 4 pieces, 2000 numbers as before), so one full search uses 4 of the 10 hourly calls. The app swallows errors there and shows an empty result.

## N13: `record_visit`
Now: at most 30 NEW visitor rows per internet address per hour (the counter stores only a hash of the address; over the limit the visit is silently ignored, the function never raises), and a retention rule run by one visit in a hundred (bounded to 500 rows): after 90 days the stored IP address and coordinates of a visit are set to empty (row, country, city, user and counts stay), and anonymous bot rows older than 30 days are deleted. Note the second rule only removes anonymous rows flagged as bots; anonymous junk rows from a flood that look like normal browsers stay (only their IP/coordinates are cleared after 90 days). Privacy Policy and Terms (the app pages and `public/privacy.html`, `public/terms.html`) got the two plain sentences; `src/i18n/catalog.json` was regenerated. No test expectation needed changing (`test-play-compliance` passes).

## N15: `resolve_login_email` - left unchanged on purpose
Login needs it: the password sign-in (`signInWithPassword`) must be given the exact address stored in Supabase Auth. For accounts created with a password in NOOB that is a made-up `...@users.nooob.xyz` address (harmless). An account created with a real email AND a password has its real address as the login address, so the function must return it, or that person cannot log in; the only way to stop returning it is to move the whole password check to a server function (the way login approval already does), which cannot be proven safe in one step. Already true today (migration 20261022000004): Google accounts without a password get a decoy, never their real address. The test proves the function is byte-for-byte unchanged and that each type resolves as before (made-up, real-email-with-password, Google, phone, unknown).
Owner check (read-only SQL): `select count(*) from auth.users u where u.email not like '%@users.nooob.xyz' and coalesce(u.encrypted_password,'') <> '';` If it is 0 nothing leaks today; if not, those people's real addresses can be learned by typing their user ID.

## L6: `android-overrides/debug.keystore`
The workflow (`.github/workflows/android-build.yml`) copies it to `~/.android/debug.keystore` only for the step "Build debug APK (for sideloading / testing)" and the in-app update file `NOOB.apk`, so people can update over an older copy. The Play bundle is a separate step ("Build signed release AAB") built only if the secret `ANDROID_KEYSTORE_BASE64` exists, signed with `release.keystore` made from the secrets `ANDROID_KEYSTORE_*`; the workflow adds that signing config itself, so the debug key is not used for the Play release. Nothing was changed. Owner should confirm: the secret `ANDROID_KEYSTORE_BASE64` is set in GitHub, Play App Signing is enabled in the Play Console, and the key fingerprint Play shows as "upload key" matches the release keystore, not the debug one. The debug key is public (anyone can sign an APK with it), so only trust the website APK as far as its download address.

## 000006 (deleted accounts), re-read for safety
Safe: on today's data (0 orphan profiles) it is a no-op (its tests pass: 34/34). Things that can surprise:
1. It runs the clean-up once at the bottom (not a dry run). It refuses if more than 25 accounts, or half of all profiles, look deleted, and saves the profile and follow rows into `deleted_accounts_cleanup_backup` first. Other content of a purged profile is not backed up (it goes by cascade).
2. `is_hidden_from_me` now also returns true for an account whose login row is missing or soft-deleted (`auth.users.deleted_at`); an extra look-up in `auth.users` per profile in every people list (small, tested). If a real person's login were ever missing from `auth.users` they would vanish from lists (the preview found none).
3. Two triggers on `auth.users`: a BEFORE DELETE that removes follows, requests, notifications about the person and mute settings (errors swallowed so a delete is never blocked), and an AFTER UPDATE OF `deleted_at` that, when a login is SOFT-deleted (for example in the Supabase dashboard), immediately deletes the person's profile and, by cascade, their posts, comments, likes and so on (a backup row of profile and follows is kept). Soft-deleting a login is therefore now as final as deleting it.
My migration does not redefine `is_hidden_from_me` (a test checks it is byte-identical before and after) and its follow rule calls the 000006 version, so the order 000006 then 000009 is required.

## Gaps closed (migration `20261114000010_privacy_gaps.sql`, test `scripts/supabase/test-privacy-gaps.mjs`, 39 checks, registered in the guard)
Run it after 000009. One `create or replace` of `user_public_json` (same signature, invoker, same grants); nothing deleted; running twice is harmless.

**Gap A, closed: `followingIds` of private accounts.** `user_public_json` used to give the list of who an account follows to every signed-in reader, private accounts included. Now:
* If the reader may see the account's follow rows (it is their own account, an admin, a non-private account, or the reader follows it), the list is as before, except that a PRIVATE account the reader does not follow is left out of it (otherwise the followers list of a private account could be rebuilt from other people's lists). The reader themselves are never left out.
* Otherwise (a private account the reader does not follow) the list is empty, except the reader's own id if that account follows the reader. The reader can already see that row, and the app uses it for "follows you" and for who may start a chat, so nothing changes there.
* `followersCount` / `followingCount` are untouched. The reader's OWN list (get_my_user) is complete and byte-identical. The admin sees everything as before. With no signed-in person (server side) the old full answer is returned.
* What users see: on a private account you do not follow, the Followers and Following lists are empty (as the follow rows already were since 000009); a public account's Following list no longer shows private accounts you do not follow; the Followers list of a private account you do not follow is empty. Everything else (names, counts, search, chat eligibility, "follows you") is identical; the test compares 99 answers (search_users, user_by_id, get_my_user for 9 readers) and 161 id lists against an independent calculation.
* App check: `FollowListPage` builds Followers from the other people's `followingIds` and Following from the target's list, `ProfileView` uses `targetUser.followingIds.includes(me)`, chat uses the same: an empty list gives an empty page, no crash, and the "follows you" case is kept by the reader-id rule above. No app change was needed.

**Gap B, NOT changed (deliberately).** A hidden (profile_hides) or suspended account's username, display name, avatar, bio, counters etc. are still readable straight from the `profiles` table by any signed-in person. Why nothing safe exists: (1) a row rule on `profiles` would apply to every function that reads `profiles` with the caller's rights; `post_json`, `reel_json`, `story_json`, comment, message and notification builders (and `search_users`' own where-clause) are not security definer, so a person hidden from the reader would show with a blank name in chats, comments and notifications, which is what must not happen; (2) column grants cannot help because the same functions need username, display_name, avatar and bio. Making all of them definer is a large change of 159 migration files' worth of functions and cannot be proven in one step. Residual exposure: a signed-in person who talks to the API directly (not the app) can list basic public-profile fields of hidden and suspended accounts, and can enumerate every account. The sensitive columns (city, extra, privacy_settings, points, suspension flag, Pro/shop fields) and the follow rows of private accounts are closed. A test (section 4) pins that this gap is unchanged.

Manual live-check scripts fixed: `live-check-phase1.mjs` re-reads points through `get_my_user`, `live-check-phase4.mjs` asks `my_suspension_status()`.
